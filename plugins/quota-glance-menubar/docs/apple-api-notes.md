# Apple API notes

Verified against current Apple documentation and first-party SwiftPM source on 2026-09-20. Research entry point: [Apple Developer search for WKWebView](https://developer.apple.com/search/?q=WKWebView). The deployment target is macOS 13 or later. Recommendations below are application design choices; cited API behavior is from the platform documentation.

## Status item and compact popover

- [`NSStatusItem.button`](https://developer.apple.com/documentation/appkit/nsstatusitem/button) is an `NSStatusBarButton?`, available since macOS 10.10. Customize its image, target, and action. Keep the status item strongly referenced for the life of the app.
- [`NSStatusItem.menu`](https://developer.apple.com/documentation/appkit/nsstatusitem/menu) disables the status item's single-click action when nonnil. To retain left-click popover behavior, leave it nil and explicitly show a contextual menu for the secondary action using [`NSMenu.popUp(positioning:at:in:) -> Bool`](https://developer.apple.com/documentation/appkit/nsmenu/popup(positioning:at:in:)) (macOS 10.6+). Verify right-click dispatch on a Mac; the general [`NSControl.sendAction(on:)`](https://developer.apple.com/documentation/appkit/nscontrol/sendaction(on:)) documentation describes legacy left-mouse tracking masks and does not establish status-button right-click behavior by itself.
- Set `contentViewController` before [`NSPopover.contentSize`](https://developer.apple.com/documentation/appkit/nspopover/contentsize): assigning the controller sets content size from its view. Then set `NSSize(width: 400, height: 620)` and anchor with `show(relativeTo:of:preferredEdge:)`. These popover APIs date to macOS 10.7. [NSPopover overview](https://developer.apple.com/documentation/appkit/nspopover).
- [`NSPopover.Behavior.transient`](https://developer.apple.com/documentation/appkit/nspopover/behavior-swift.enum/transient) dismisses on outside interactions; menus and panels that become key only when needed are exceptions. Apple deliberately leaves the exact dismissal interactions unspecified. Keep one content controller and web view as the popover opens and closes.
- Checked on 2026-10-10: the status item sends its action on left-mouse-down (`sendAction(on: [.leftMouseDown, .rightMouseUp])`), as system menu bar items act on press. A right-click still acts on release: a status item whose action is sent on right-mouse-down can stay highlighted, and the next click then only clears the highlight and sends no action ([report by Jesse Squires, 2019](https://www.jessesquires.com/blog/2019/08/16/workaround-highlight-bug-nsstatusitem/), using this same mask as the workaround; not an Apple contract). Control-click arrives as a left-mouse-down, which that report found unaffected. A transient popover may close itself in response to that same press before the action runs, and [`isShown`](https://developer.apple.com/documentation/appkit/nspopover/isshown) counts a popover as closed once `close()` or `performClose(_:)` has been invoked, so `isShown` alone cannot tell the action that its press closed the popover. The app records when each close begins in [`popoverWillClose(_:)`](https://developer.apple.com/documentation/appkit/nspopoverdelegate/popoverwillclose(_:)) (macOS 10.10+) and treats a press within half a second of it as the press that closed the popover. Verify with a physical click and with tap-to-click on a Mac.

## Web content, sessions, and refresh

- [`WKWebView`](https://developer.apple.com/documentation/webkit/wkwebview) (macOS 10.10+) is a native view for HTML, CSS, and JavaScript; Apple explicitly recommends it when content changes frequently. Load the hosted page with `load(URLRequest(url: ...))`; there is no need to bundle or copy its HTML/CSS.
- Set `configuration.websiteDataStore = .default()` before creating the web view. [`WKWebsiteDataStore.default() -> WKWebsiteDataStore`](https://developer.apple.com/documentation/webkit/wkwebsitedatastore/default()) (macOS 10.11+) retains website data on disk between sessions. This establishes persistence for the app, not shared authentication with Safari.
- [`reloadFromOrigin() -> WKNavigation?`](https://developer.apple.com/documentation/webkit/wkwebview/reloadfromorigin()) (macOS 10.10+) reloads the **current** page and performs end-to-end revalidation with cache-validating conditionals where possible. Use it for an explicit refresh without destroying the web view. A refresh while the user is signing in or filling a form can interrupt that work; reopening the popover should preserve the current page. Checked on 2026-10-10: current WebKit source reloads the main resource without revalidating it (`FrameLoader::reload`: "We don't have a mechanism to revalidate the main resource without reloading at the moment"), and treats a load of the URL already showing the same way, so Reload Page downloads the page again. [FrameLoader.cpp](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/loader/FrameLoader.cpp) is implementation evidence, not an Apple contract.
- [`URLRequest.CachePolicy.useProtocolCachePolicy`](https://developer.apple.com/documentation/foundation/nsurlrequest/cachepolicy-swift.enum/useprotocolcachepolicy) is the default policy: a cached response that must be revalidated is checked with the originating source before it is used. Quota Glance serves the page with `Cache-Control: no-cache` and an ETag, so from 0.5.0 dashboard loads use this policy and get a 304 while the page is unchanged. Through 0.4.0 they used [`reloadIgnoringLocalCacheData`](https://developer.apple.com/documentation/foundation/nsurlrequest/cachepolicy-swift.enum/reloadignoringlocalcachedata), which loads from the originating source without satisfying the request from existing cache data, so every load downloaded the whole page. Do not describe either API as bypassing every service-worker/server cache or instantly pushing deployments into an already loaded document.
- [`NWPathMonitor`](https://developer.apple.com/documentation/network/nwpathmonitor) (macOS 10.14+) observes network path changes. The app uses a satisfied path only to bring a waiting retry forward; polls never wait for one, because a dashboard on the same Mac needs no network path.

## Navigation and web dialogs

- [`webView(_:decidePolicyFor:decisionHandler:)`](https://developer.apple.com/documentation/webkit/wknavigationdelegate/webview(_:decidepolicyfor:decisionhandler:)-2ni62) takes a `WKNavigationAction` and a completion accepting `WKNavigationActionPolicy` (macOS 10.10+). Always complete its decision handler. Implementing the newer overload with `preferences:` suppresses calls to this overload. Current SDK documentation marks these delegate callbacks `@MainActor` and their completion handlers `@MainActor @Sendable`.
- Recommended routing: compare scheme, host, and effective port; allow same-origin navigation across paths so hosted login/session and console pages continue in the persistent web view. Route intentionally clicked external HTTP(S) links through `NSWorkspace.shared.open`. An origin policy is an app choice, not an authentication mechanism. Do not move login to a different browser and expect its session to populate this web view.
- [`WKNavigationAction.targetFrame`](https://developer.apple.com/documentation/webkit/wknavigationaction/targetframe) is nil for a new window. Handle that case so `target="_blank"` links work. [`webView(_:createWebViewWith:for:windowFeatures:) -> WKWebView?`](https://developer.apple.com/documentation/webkit/wkuidelegate/webview(_:createwebviewwith:for:windowfeatures:)) (macOS 10.10+) permits returning nil; if returning a new web view, Apple requires using the supplied configuration. For this one-popover wrapper, routing the request and returning nil avoids additional native windows.
- Implement [`webView(_:runJavaScriptAlertPanelWithMessage:initiatedByFrame:completionHandler:)`](https://developer.apple.com/documentation/webkit/wkuidelegate/webview(_:runjavascriptalertpanelwithmessage:initiatedbyframe:completionhandler:)) and [`webView(_:runJavaScriptConfirmPanelWithMessage:initiatedByFrame:completionHandler:)`](https://developer.apple.com/documentation/webkit/wkuidelegate/webview(_:runjavascriptconfirmpanelwithmessage:initiatedbyframe:completionhandler:)) (macOS 10.10+) because hosted actions can invoke `alert()` and `confirm()`. Alert completes with `Void`; confirm completes with `Bool`. Apple specifies one OK button for alert, OK/Cancel for confirm, and identifying the controlling site, for example using `frame.request.url?.host`. Ensure cancellation/dismissal also completes the callback.
- Checked on 2026-10-10 in current WebKit source (implementation evidence, not an Apple contract): WebKit gives the page each key first. For an Escape the page leaves unhandled, the web process runs Escape's `cancelOperation:` command at the keypress ([WebPageMac.mm](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/WebProcess/WebPage/mac/WebPageMac.mm) defers it there) and, since WebCore has no such command, the UI process performs it up the AppKit responder chain from the web view (`WebViewImpl::executeSavedCommandBySelector` in [WebViewImpl.mm](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/UIProcess/mac/WebViewImpl.mm)). A key that stays unhandled is re-sent through `[NSApp sendEvent:]` (`WebViewImpl::doneWithKeyEvent`). The dashboard controller closes the popover from [`cancelOperation(_:)`](https://developer.apple.com/documentation/appkit/nsstandardkeybindingresponding/canceloperation(_:)), or from `keyDown(with:)` for Escape, which it gets while the loading or error view has focus. WebKit's default Escape close of a modal `<dialog>` (`EventHandler::defaultKeyboardEventHandler` in [EventHandler.cpp](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/page/EventHandler.cpp)) does not mark the key handled, so the command would still run and close the popover too. The bridge therefore closes an open modal dialog itself (a cancelable `cancel` event, then `close()` unless the page cancelled it) and calls `preventDefault()` on the keydown; WebKit then counts the key handled and dispatches no keypress, so Escape closes the dialog and leaves the popover open. Verify on a Mac with a page dialog open.

## Optional launch at login

[`SMAppService.mainApp`](https://developer.apple.com/documentation/servicemanagement/smappservice/mainapp) is available on macOS 13 and configures the main app as a login item without a separate helper executable. [`register() throws`](https://developer.apple.com/documentation/servicemanagement/smappservice/register()) schedules the main app for subsequent logins, subject to user approval. Present actual [`status`](https://developer.apple.com/documentation/servicemanagement/smappservice/status-swift.enum) (`notRegistered`, `enabled`, `requiresApproval`, or `notFound`) instead of treating a saved preference as registration success. Use `unregister()` to disable and `openSystemSettingsLoginItems()` when approval is needed. [SMAppService overview and methods](https://developer.apple.com/documentation/servicemanagement/smappservice).

## Build and local packaging

- Universal builds through v0.4.0 (superseded below): SwiftPM accepts repeated `--arch` arguments, but the build system depends on toolchain version. [SwiftPM 6.0 source](https://github.com/swiftlang/swift-package-manager/blob/swift-6.0-RELEASE/Sources/CoreCommands/Options.swift) forces the Xcode build system when more than one architecture is supplied; [current source](https://github.com/swiftlang/swift-package-manager/blob/main/Sources/CoreCommands/Options.swift) uses `swiftbuild`. For a predictable CLI script, run `swift build -c release --arch arm64` and separately `swift build -c release --arch x86_64`, locate each product using `--show-bin-path` with the matching options, then merge with `xcrun lipo -create -output ...`.
- Universal builds through v0.4.0 (superseded below): Apple explicitly documents compiling one executable per architecture and merging with `lipo` for custom build scripts. Universal means both `arm64` and `x86_64`; either type of Mac can build both, while running the ARM slice requires Apple silicon. [Building a universal macOS binary](https://developer.apple.com/documentation/apple-silicon/building-a-universal-macos-binary).
- Current build (2026-10-10): the app is Apple silicon only, so `build-app.sh` runs a single `swift build -c release --arch arm64` and needs no `lipo` merge. Sparkle's SwiftPM artifact contains only a universal framework, so it is copied with `ditto --arch arm64`, which thins universal Mach-O binaries during the copy ([ditto(1)](https://keith.github.io/xcode-man-pages/ditto.1.html)). [`LSArchitecturePriority`](https://developer.apple.com/documentation/bundleresources/information-property-list/lsarchitecturepriority) only prioritizes an architecture within a universal binary, so the single-architecture app does not set it.
- Package the resulting executable in an `.app` bundle before signing. `codesign --force --sign - "Quota Glance.app"` applies an ad-hoc signature: Apple's [`SecCodeSignatureFlags.adhoc`](https://developer.apple.com/documentation/security/seccodesignatureflags/adhoc) documentation specifies the dash pseudo-identity and explains that it seals code without a signing identity. This is local packaging, not Developer ID signing or notarization. The native build, bundle signing, popover interactions, and login-item registration must be verified on macOS; Linux cannot establish their runtime behavior.
