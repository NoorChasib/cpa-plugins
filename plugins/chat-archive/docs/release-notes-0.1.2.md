# Chat Archive 0.1.2

Stores compressed bodies that 0.1.1 dropped, keeps secret-shaped ids and paths out of every part of an import envelope, keeps drop counts across a crash, and ships `chat-archive-import` 0.1.2.

## What changed since 0.1.1

- **Bodies compressed with zstd, deflate or br are stored.** A request or response body labelled with `Content-Encoding` gzip, zstd, deflate or br, alone or stacked (`gzip, br`), is decoded before the split and masked like any other body, with flag `gunzipped` for gzip and `content_decoded` for the others. A client that compresses its request body (Codex sends zstd) is therefore stored, not dropped as `parse_error`. Repeated `Content-Encoding` field lines are combined in order, and the header is read in any key case. The response id and Responses status of a decoded non-stream body are read from the decoded bytes, so the exchange stays linkable to its transcript. See [REFERENCE.md](../REFERENCE.md).
- **Decoding is bounded.** Each layer's decoded size is capped, all layers together at twice that cap, and a body naming more than three codings is not decoded. A Brotli stream whose declared window is over the cap (and over 4 MiB) is refused before its decoder allocates the window. Decoding stops at the masking deadline and at shutdown's drain. A body that is whole valid JSON is never fed to the deflate or br decoders, and a deflate stream must end exactly where the body ends, so a plain body under a stale label is never "decoded" into garbage. What cannot be decoded keeps its metadata only, with `dropped: parse_error`, as before.
- **Secret-shaped ids and paths stay out of import envelopes.** An `import.file` body carries a masked `file_key`, and record ids and joined JSON pointers are masked in `import.record` bodies. A key segment the masker would change is replaced by a hash of it, and a locator path's identifying segments are hashed the same way, so a directory, session file or run id that looks like a secret never leaves the machine in a key, a tombstone or a locator. Records whose ids are clean keep their 0.1.1 keys byte for byte, so nothing already archived is uploaded again. An extracted value whose JSON pointer would itself need masking stays inline, so every pointer still resolves. See [What leaves the machine](importer.md#what-leaves-the-machine).
- **A `mask_violation` dead letter names its rules.** `requeue --reason mask_violation --remask --dry-run` prints the rule ids that would still refuse the rebuilt record and the parts they are in (`key`, `loc`, `body`, `pieces`), or `rules=none` when a requeue with `--remask` now goes through.
- **Records archived under a 0.1.1 key are reconciled, not stored twice.** When a record's key changes while its body does not (a secret-shaped workflow run id, or clean segments that join into a secret), the envelope also carries `prior_key_sha256`, the sha256 of its 0.1.1 key, never the key itself. An archive that advertises `accepted.prior_key_sha256` moves the stored record to the new key. Against an archive without that capability the importer sends neither key: the record becomes a local `key_migration` dead letter, and `requeue --reason key_migration` sends it once the archive supports it. This case is rare.
- **Drop counts survive a crash.** The plugin saves its `dropped.*` counters in its outbox, and the next boot reports a crashed boot's counts in a heartbeat with state `recovered`, so a crash no longer loses up to a minute of drop counts. A recovered record the archive refuses for good is dropped and counted instead of retried forever.

## Upgrading

In CPA's Plugin Store, refresh the catalog and select **Update** for Chat Archive. Your configuration and local outbox are kept. Bodies that 0.1.1 dropped as `parse_error` were never stored and are not recovered. The importer is not part of the plugin package: rebuild `chat-archive-import` from this release's source ([build](importer.md#build)). After that, `chat-archive-import requeue --reason mask_violation --remask` retries records an earlier importer could not mask.

## Known limits

- A labelled body that does not decode, names an unknown coding or more than three codings, or is valid JSON but not an object, is still dropped as `parse_error` by design: compressed bytes cannot be mask-scanned.
- `key_migration` records wait for an archive that reconciles prior keys; the requeue is manual.
- The 0.1.1 limits still apply: requeue `full=1` and `split=1` are not supported, binary attachments are stored raw, and only Linux amd64 is supported.
