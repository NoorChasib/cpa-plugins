# Chat Archive 0.1.5

Keeps the retry of a Responses WebSocket turn that CPA v8.0.76 and later fail over in place under the same request ID. **Update the archive server first.**

## What changed since 0.1.4

- **The retry of an in-place WebSocket failover is stored.** From v8.0.76, when a Responses WebSocket turn's pinned credential fails before any output, CPA retries the turn on another credential, on the same socket and under the same request ID. 0.1.4 numbered the retry's begin, attempt and completion as if they were new. So they collided with the failed attempt's keys, the retry's records were skipped as duplicate keys, and the exchange kept the failed attempt's outcome. 0.1.5 continues the request's numbering across both lifecycles. The failed attempt keeps `ex/<request id>/completion`, and the retry's completion is written at `ex/<request id>/completion/<started_at>`. When the plugin can prove which begin replayed the turn, the retry's completion names it in `lifecycle_input_seq`, so the archive does not show the replay as a new input. See [REFERENCE.md](../REFERENCE.md#reused-requestids).
- **Each attempt's stream is stored once, under its own lifecycle.** 0.1.4 discarded what the failed attempt had buffered when the retry's stream began, or wrote the retry's half-built stream under the failed attempt's status. 0.1.5 parks a stream attempt until the completion that owns it is processed. A completion writes only the stream attempts its lifecycle times prove are its own. When that cannot be told yet, the completion waits for the evidence and releases nothing.
- **Completion keys stay apart when the plugin has lost its record.** The plugin keeps a closed request's numbering for 10 minutes, carries it across an update, and leaves it behind when the idle sweep evicts a request. When even that is gone, a completion whose bare key is already taken is moved to its `started_at` key, by the outbox or after the archive answers `conflict`. Nothing is skipped as a duplicate.
- **New status counters.** `reused_request_id`, `lifecycle_unverified`, `numbering_evicted`, `segments_parked`, `ownership_held`, `segments_uncertain`, `completion_rekeyed.outbox` and `completion_rekeyed.archive` are on the status route's `counters`.
- **Native acceptance also runs on CPA v8.0.76.** A new required phase builds CPA v8.0.76 from pinned source and forces an in-place WebSocket failover: the pinned credential answers turn 2 with a usage-limit 429 before any output. It requires one bare and one `started_at` completion key for that request ID, begins `input_seq` 0 and 1, `lifecycle_input_seq` 1, `reused_request_id` 1 and `dropped.duplicate_key` 0. The other phases still run on CPA v8.0.73.
- **A slow disk no longer drops a group of captures at once.** 0.1.4 dropped a group of up to 50 envelopes as `dropped.disk_hard` when its outbox write timed out, or after three quick retries of a busy database. 0.1.5 retries the group in order, with a backoff doubling from 25 ms, while the write fails busy, locked or with an I/O error or times out, for up to 20 s and never past a stop's deadline, even when a retry is stuck in disk I/O that cannot be cancelled. A disk that stays stalled longer is handled as in 0.1.4, and later captures are probed and written as soon as 0.1.4 would have tried them.
- **Nothing changes for a request ID that CPA uses once.** Keys and bodies are the same as 0.1.4's, except in the corner listed under Known limits.

## Upgrading

Update the archive server to the release that decides an exchange by its latest-started completion before you update this plugin. An older server stores the new keys, but it renders the replayed input as a new input and can pair the failed attempt's partial response with the turn's input. In one rare case it also ends the exchange with the failed attempt's outcome: the plugin lost every record of the request before the retry completed, and the failed attempt's completion arrived even later.

Then, in CPA's Plugin Store, refresh the catalog and select **Update** for Chat Archive. Nothing changes in the configuration. The outbox gains a `completion_numbering` table, which 0.1.4 ignores, so your settings and local outbox are kept. The update runs 0.1.4's stop, which keeps capturing the exchanges already open, so no quiet switch is needed. Going back to 0.1.4 works the same way, but under CPA v8.0.76 and later 0.1.4 drops the retry again.

Only then move CPA to v8.0.76 or later. Exchanges stored under CPA v8.0.76 with 0.1.4 cannot be repaired: the retry's records were never stored.

## Known limits

- **A non-succeeded stream's completion can arrive up to 2 minutes late.** When the plugin cannot prove which lifecycle a stream attempt belongs to, it holds the completion until a later event or the other completion settles it, or for one to two minutes. That also happens on a request ID that is never reused, for a stream that spans a restart or update or follows an undecodable hook. A `succeeded` completion is never held. The stored response is the same as 0.1.4's. One corner keeps more: a duplex stream that ends `failed`, `canceled` or `rejected` after the client sent a follow-up between two bootstrap header-inits keeps the earlier attempt as an extra partial response, which 0.1.4 discarded.
- **A completion settled without evidence can label a stream with the wrong outcome.** This needs the failed attempt's lifecycle to complete only after the whole retry ran, and the retry's completion to be missing for the next minute. Both attempts are stored, and the retry's completion is still written. The settle is counted in `segments_uncertain`.
- **The replayed input can show twice.** When the plugin cannot prove which begin opened the retry, it leaves `lifecycle_input_seq` out, and the archive shows the replay as an input. This happens after a decode error, a restart or update, an idle eviction, or four or more duplex follow-ups before the completion was processed. It is counted in `lifecycle_unverified`. No real input is hidden.
- **Numbering can still collide if the record is lost between the two lifecycles.** If more than 256 requests close in the same shard, or 10 minutes pass, between the failed attempt's completion and the retry's first hook, the retry's begin, attempt and response numbering restarts and collides as `dropped.duplicate_key`, as in 0.1.4. CPA starts the retry right after the failure, with no wait. Completion keys are not affected. Lost records are counted in `numbering_evicted`.
- **An update in the middle of a reused request ID cannot repair 0.1.4's numbering,** because 0.1.4 kept no record of closed requests. Completion keys are still kept apart while 0.1.4's completion is in the outbox or the archive.
- A request ID of 167 bytes or more has no room for the `started_at` suffix and keeps 0.1.4's behaviour. CPA's request IDs are 36 bytes.
- The 0.1.4 limits still apply, except the CPA v8.0.76 one, which this release fixes. Payloads from CPA v8.0.74 to v8.0.76 otherwise decode the same as before.
